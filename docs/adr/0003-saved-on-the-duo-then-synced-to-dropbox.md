# Canvases are saved on the Duo first, then synced to Dropbox, with full Dropbox access

Pen work cannot be lost to a dropped connection, and the laptop's agents have to read what Zach drew. So every change is saved on the Duo first, and a canvas is synced to a Vellum folder in Zach's Dropbox, which the laptop already mirrors to its disk. We considered iCloud Drive, which the laptop would need iCloud for Windows to read, and keeping canvases only on the Duo, which would leave the laptop nothing to read until a send.

Vellum asks for full Dropbox access rather than an app folder, because the PDFs Zach marks up already live in his project folders. Sign-in uses Dropbox's OAuth flow with PKCE, which needs no app secret, so the public repository holds no Dropbox secret. The app key is kept out of the repository anyway.

## Amendment (#12): how a canvas syncs

Zach's decisions on #9 and #12 (2026-11-01 and 2026-11-02) and what the builder worked out from them:

- **Where.** Each canvas folder is mirrored to `Dropbox/Vellum/<name> <short id>`, for example `Boiler 4 walkdown 7f3a`: the canvas's name when it was made, made safe for Dropbox and for the laptop's Windows disk (`\ / : * ? " < > |` and control characters become `-`, white space runs become one space, leading dots and trailing dots and spaces go, at most 60 characters and 180 UTF-8 bytes; nothing left is "Canvas"), then the first four hex digits of its id, lengthened two at a time only if another canvas's folder already has that name. The name is fixed in `canvas.json` (`dropboxFolder`) when the canvas is made and never follows a rename, so the laptop's paths stay put; the current name is in `canvas.json`. A canvas made before #12 has no `dropboxFolder`; it takes its name at its first sync, kept in the sync ledger (sync never writes the canvas's own files).
- **When.** A canvas syncs when Zach leaves it, and every canvas waiting to sync (the one on screen too) when the app goes to the background, in the time iOS gives a background task; what doesn't finish waits in the outbox. Nothing uploads while he draws: the canvas on screen is skipped until then. Saving on the Duo is unchanged. Leaving a canvas waits on nothing: it hands the canvas to the sync actor, which reads it through the canvas saver's queue, behind the flush that closing starts.
- **How.** Over Wi-Fi or cellular alike, with no Low Data Mode check, since only what changed goes (ADR-0014's #12 amendment). Deleting a canvas moves its Dropbox folder to `Vellum/.deleted/` rather than erasing it; a second delete of the same name is kept beside the first (`<folder> (1)`).
- **Offline.** See ADR-0010's #12 amendment.
- **The Duo is the only writer** (ADR-0010). Vellum writes `canvas.json` and `ink.snapshot` with Dropbox's `update` mode and the revision it last wrote, so a file changed or removed in Dropbox meanwhile is noticed (a conflict). Then the Duo's copy wins: the whole canvas is uploaded again, replacing what is there, and the sync ledger notes the file and the time (`CanvasSyncRecord.replaced`). Dropbox keeps the replaced version in its version history, so nothing the laptop wrote is lost either, and the Duo's ink is never touched. Log parts are written with `overwrite` (a part's bytes at its offset are always the Duo's) and sheets' PDFs with `add` (a PDF is named by its content hash, so one already there holds the same bytes). What a canvas folder deleted on the laptop does is in the #37 amendment below.
- **Signing out** forgets what was uploaded (the next sign-in may be another Dropbox): after signing in, every canvas uploads whole once, replacing what it finds.
- **What the screens say** (decision 4, variant B of `prototype/sync-status`): the status bar says "Synced to Dropbox"; "Saved on this Duo" once the canvas changes (it syncs when Zach leaves); "Saved · offline" in amber with a warning sign while changes wait for a connection; "Sync failed" with a small Retry; "Signed out" with a small Sign in. Saving still comes first: "Not saved: will retry" shows over all of these, and the offline wording always starts "Saved" so the two ambers never read alike. Each is shorter than "Saved on this Duo", so the tool prompt keeps its room; VoiceOver and the Canvases list say them in full ("waiting for Dropbox", "sync failed · will retry", "Dropbox signed out"), and the list's banner carries Retry and Sign in. A build without a Dropbox key says only "Saved on this Duo", as before.

## Amendment (#37): a canvas folder deleted on the laptop

A canvas's Dropbox folder deleted on the laptop, or a file deleted from one (its `canvas.json`, snapshot, a sheet's PDF or a log part), makes the canvas upload whole once, as for a file changed underneath: everything is written with `overwrite`, the ledger notes it (`CanvasSyncRecord.replaced`, file `folder`), and later syncs go back to only what changed. The canvas on the Duo is never touched, and a re-upload cut short carries on at the next sync like any other.

It is found by the folder check, not by a normal sync, because Dropbox gives no answer on a normal sync that could say it. A normal sync after new strokes is one `files/upload` of a log part with `overwrite`, and an upload makes every folder on its path; none of its arguments (`mode`, `autorename`, `mute`, `strict_conflict`, `client_modified`, `property_groups`) makes it fail when the folder is missing, its errors (`WriteError`) have no "not found", and its reply (`FileMetadata`) says nothing about the folder. Uploading to `id:<folder id>/…` would fail for a deleted folder, but no request a sync makes returns a folder's id, so learning it would add a request to every canvas's first sync. Checking `canvas.json` on every sync would add a request to every sync. So the check is one request, made before the next upload after the sync engine starts, after the app comes back to the foreground and after the connection returns, and only when there is something to upload. The first lists `Vellum/` recursively (`files/list_folder`); after that it asks only what changed since (`list_folder/continue`, with the cursor kept in the sync ledger), usually a handful of entries. A deletion that leaves an expected file missing, or takes away any of the current log generation's parts, marks the canvas. The Duo's own deletes (a replaced log generation, a deleted canvas's folder moved to `Vellum/.deleted`) don't count; after a log restart, which only damage on the Duo causes, the canvas uploads whole once more than it needs.

`canvas.json` and the snapshot are now written with `strict_conflict` alongside `update`. Without it Dropbox writes a file that has been removed as if it were new, so a `canvas.json` deleted on the laptop came back alone instead of being noticed.

What this leaves: a folder deleted while the Duo stays in the foreground and online is found at the next foreground, relaunch or reconnect, not straight away; until then the laptop sees an incomplete folder, as it did before #37. A canvas with nothing to upload is not checked until it has.
