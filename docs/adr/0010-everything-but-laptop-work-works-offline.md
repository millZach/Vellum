# Everything but laptop work works offline

Zach marks up drawings in plants and basements with no signal. Drawing, text boxes, measuring, dimensions, recording meetings, opening any sheet or drawing already on the Duo and searching the drawing index all work offline. Anything that needs the laptop (sending a job, plotting a drawing to PDF, transcribing and summarizing a meeting) waits on the Duo and goes when the Duo is online and the laptop is reachable. Pinning project folders for offline in advance was considered and left for later; what Zach has opened stays on the Duo.

Vellum edits a canvas only on the Duo. The laptop adds results beside a canvas and never changes the canvas itself, so a canvas has one writer and syncing it to Dropbox has no conflicts to resolve.

## Amendment (#11): a placed sheet's PDF stays on the Duo

A PDF picked in Add sheet, or opened in the drawing viewer (#69), is downloaded once, into the app's Caches folder, named by its Dropbox content hash (`SheetPDFs`), so picking or opening it again, from any canvas or from search, downloads nothing. Placing a sheet copies it into the canvas folder (ADR-0014's #11 amendment), and the sheet is drawn from that copy ever after, so a placed sheet opens offline and reopening a canvas never downloads anything. Caches may be cleared by the system; that costs only a download the next time the PDF is picked.

## Amendment (#12): the sync outbox

Syncing a canvas never needs a connection to save it. The sync outbox (uploads and deletes still to do in Dropbox) is part of the sync ledger, one small JSON file in the app's Application Support folder (`Sync/ledger.json`), written whole and flushed to storage at every change, so it survives a crash or a relaunch. It is not in Caches, which the system may clear: that would lose deletes made offline and make every canvas upload whole again. It holds folder names, Dropbox revisions, byte counts and canvas ids, never a token or any ink. `NWPathMonitor` says when the Duo is online; when the connection returns, the outbox goes at once. A failure is retried after 5 s, doubling to at most five minutes; Retry goes at once. A failed or half-done sync changes nothing on the Duo: sync only reads the canvas folder, through the canvas saver's queue, and every step leaves Dropbox's copy whole, so the next attempt carries on from the last step that finished.

## Amendment (#41): the symbol library

The symbol library is kept on the Duo, so placing and saving symbols works offline; it syncs both ways with `Dropbox/Vellum/Symbols` when there is a connection (ADR-0016). The library, not a canvas, is the one thing the laptop writes that the Duo reads.

## Amendment (#68): the index copy

Searching the drawing index works offline because the Duo keeps an index copy in the app's Application Support folder (`DrawingIndex/`), not Caches, which the system may clear: `index.json` (the manifest it was last swapped in with), `shards/<hash>.json` and `thumbnails/<hash>.png`, each named as in Dropbox (ADR-0017). It is refreshed at launch, when the app comes back to the screen, when the connection returns, on signing in to Dropbox and on a pull to refresh on the Drawings tab, one refresh at a time, off the main thread. A refresh lists `Dropbox/Vellum/Index` once; when `index.json`'s content hash there is the copy's manifest's, nothing else is asked. Otherwise it downloads the manifest and only the shards whose names the Duo has not got, checking each against the hash its name gives, and writes the new manifest over the copy's only once every shard it names is on the Duo, so a refresh cut short (offline, a failed download) leaves the copy whole and the next one finds the shards that did arrive. Before the swap every shard the new manifest names is read: one named right but not the index's shape (damaged at the laptop, or a newer format) keeps the copy as it was, as ADR-0017 says, and the Drawings tab says so once. Shards nothing names are deleted after the swap, and thumbnails nothing names when the copy is next read. A manifest in a format other than 1 is refused: the copy stays as it was, and the Drawings tab says so once per format. The decisions are `DrawingIndexPlan` in VellumCore.

Thumbnails come down one at a time as a row shows them online, and are kept with the copy; a thumbnail never shown online is blank offline. Fetching every thumbnail on each new generation was considered, so offline rows would all have pictures, and rejected: at Zach's scale that is tens of thousands of requests on the first refresh over a phone connection, for pictures of 128 pixels. "Not on this Duo" is decided as `docs/drawing-index-format.md` says, against the PDFs kept in `SheetPDFs` (Caches), and only while offline: a PDF never opened on the Duo can't open without a connection.

## Amendment (#69): the drawing viewer

A drawing opened from the Drawings tab's search is shown from the same `SheetPDFs` copy Add sheet keeps, one shared copy with one download path, so a PDF opened once opens offline with no download and is the same file Add sheet and placing use; Add sheet and the viewer asking for one path at once share one download. One the Duo has not got is downloaded by its Dropbox path in one request and kept under the content hash Dropbox gives for exactly those bytes (the download's `Dropbox-API-Result`), so a PDF plotted again since the laptop read it is never kept under the old hash. Each kept PDF also remembers the path it came from (`paths.json` beside the PDFs, in Caches with them), so the viewer and the "Not on this Duo" marker find it by its path when the index's hash is stale or missing, offline and after a relaunch. Offline, a drawing whose PDF is not kept here does not open: the Drawings tab says why, and its row says "Not on this Duo", decided the same way (`DrawingOpening.decide`, `DrawingMarker.of`). A PDF kept only in a canvas folder (placed, then cleared from Caches) is not looked for: the viewer treats it as not on the Duo until the next download.

## Amendment (#70): plot requests wait on the Duo, and the plot watch

Opening a DWG with no PDF asks the laptop to plot it (ADR-0018). The request is kept in the plot ledger, one small JSON file in Application Support (`Plots/requests.json`), written whole and flushed at every change as the sync ledger is, so a request asked offline is in the sync outbox through a crash or a relaunch: the row and the viewer say "Queued on this Duo", and it goes when the connection returns, retried after `CanvasSync.backoff` on a failure. It has a ledger of its own rather than a place in the sync ledger, because a plot request has its own life after it is sent (an answer to read, a PDF to take, a request to delete), which the canvas sync engine knows nothing of. The ledger holds request and entry ids, DWG paths and layout names, never a token or a drawing. An ask counts only once the ledger has saved it: when it can't be saved (a full Duo), or the ledger's folder can't be opened at all, nothing is queued or sent and the viewer says "Couldn't save the request" with Try again, rather than showing "Queued on this Duo" for a request a relaunch would lose.

While a request is open the plot watch looks for its answer: one small download of the answer and, at most once a minute, the check-in's metadata, every 5 seconds for a request's first 2 minutes (a plot is usually answered within that) and every 30 seconds after, for as long as it stays open: about 13 requests a minute at first and 3 after, each about a kilobyte (`docs/perf/baselines/plot-requests.json`). The check-in is looked at once a minute whatever the answers do, so a laptop that comes back on goes from "Waiting for the laptop" to "Plotting on the laptop" at the next look, within a minute. It doesn't look with nothing open, offline, signed out or with the app in the background, and the app leaving the screen stops a look part way: nothing more is sent or fetched after the transfer under way. It looks at once when the app is back. A listing of `Vellum/Plots/requests` with a cursor (ADR-0018 allows either) would cost one request a look instead of two at most, but its reply carries every Duo's requests and answers, and the answer still has to be downloaded; one download of the one answer is smaller.

A `done` answer's PDF is downloaded once, from the answer's path, through the same `SheetPDFs` as the viewer, Add sheet and placing (#11, #69), kept under the answer's content hash; only then is the request deleted. The PDF is checked through `SheetPDFs` before every delete, not taken on the name saved in the ledger, so one the system cleared from Caches across a relaunch comes down again first. The plot is remembered with the entry in the plot ledger until the drawing index lists the entry's PDF, so the drawing opens offline, and its row never goes back to "No PDF yet" in between. Once the index lists it, the plot stays in the ledger while the index's PDF for that drawing is that plot, so the laptop's note about it (references it couldn't find, the fallback page setup) shows however the drawing is opened; the index listing another PDF forgets it. A `failed` answer's reason is kept the same way until Zach asks again. A plot that has come in opens offline like any PDF opened once; one the laptop finished while the Duo was offline says "Plotted, not downloaded" until it is back online. A plot that comes in while Zach isn't looking at that drawing in the viewer puts up the plot banner at the top of whichever tab is showing. The banner takes its own room there (a top safe-area inset), so every screen's controls, an open canvas's top bar and rails among them, move down below it while it shows and none is ever covered; the canvas itself ignores the safe area and isn't resized.
