# Vellum talks to Dropbox with its own small client, not SwiftyDropbox

Vellum signs in to Dropbox and calls its API with a small client of its own rather than Dropbox's SwiftyDropbox SDK. Sign-in is OAuth 2 with PKCE (ADR-0003): `ASWebAuthenticationSession` opens Dropbox's authorize page with an S256 challenge and `token_access_type=offline`, Dropbox sends the code back to `db-<app key>://2/token`, and the code and the verifier are traded for a four-hour access token and a refresh token. No app secret is used anywhere. Everything that decides something (the verifier and its SHA-256 challenge, the authorize URL, reading the callback, reading token replies, when to renew, renewing once on a 401, listing folders across pages, signing out offline, and what the screen shows at each step) lives in `VellumCore`'s `DropboxSession` and `DropboxConnection` and runs in `swift test` on Forge's Linux Swift, against a scripted Dropbox. The app adds only the Keychain store, a `URLSession` transport and the sign-in sheet.

The tokens are one Keychain item, readable after first unlock on this device only, and are never written to UserDefaults, a file or a log; their printed descriptions are redacted. Signing out removes the tokens from the Keychain first and shows signed out at once, then revokes the token with Dropbox in the background, renewing a lapsed access token first, with a four-second deadline; offline, refused or too slow, Vellum quietly says Dropbox wasn't told or didn't confirm. Only a Keychain that won't delete the tokens stops a sign-out, and then Dropbox is not told and Vellum says it is still signed in. Signing out wins every race: a refresh, sign-in or folder load in flight when it starts never writes tokens back or shows the signed-in screen again.

The client keeps traffic small, because how fast Vellum feels comes first. The Keychain is never touched on the main actor: the session reads it once, off the main actor, when the Drawings tab first appears, and writes it only when the tokens change. A folder's listing and Dropbox's cursor for it are kept in memory and in a small file in Caches (folder names and cursors, never a token; removed on sign-out), so a later look asks `files/list_folder/continue` only for what changed, and asks nothing within a minute of the last check unless Zach pulls to refresh. Callers asking at once share one listing and one token renewal, and the first page of a new listing shows while the rest arrive.

The app key reaches the app only as the `DROPBOX_APP_KEY` build setting. `.github/workflows/testflight.yml` passes the repository secret of that name, and `Scripts/testflight.sh` refuses to archive without one; every other build (pull requests, CI, the simulator captures) keeps the placeholder `not-set-up` from `apps/ios/Config/Vellum.xcconfig`, and a local build on a Mac can set the key in the gitignored `apps/ios/Secrets.xcconfig`, which that file includes when it exists (`docs/dropbox.md`), and the app says "Dropbox isn't set up in this build" instead of failing. The key is not a secret, since it ships inside the app, but it stays out of the public repository as ADR-0003 asks.

## Considered options

- **SwiftyDropbox** covers the whole API and handles PKCE itself, but it is a large generated runtime dependency that Vellum would be locked to for every later Dropbox ticket, it cannot be built or tested on Forge's Linux Swift, and its sign-in and token storage are its own, so ADR-0003's and the brief's Keychain and no-secret rules would have to be checked inside someone else's code. Vellum needs a handful of endpoints: the token endpoint, token revoke, `files/list_folder` and later download, upload and longpoll for #11 and syncing canvases. Each is one JSON POST that the same client takes on.
- **Adding swift-crypto for SHA-256** was passed over: CryptoKit is not on Linux, and one hash per sign-in is a 60-line function checked against the published test vectors.

## Consequences

Each later Dropbox call (download a PDF, upload a canvas, content-hash checks) is written into `DropboxSession` with its own tests. Dropbox's upload sessions for large files and its rate-limit backoff are Vellum's to write when they are needed.

## Amendment (#11): PDFs in listings, and one download endpoint

Add sheet browses Dropbox with the same listing calls (`files/list_folder` and `/continue`), which now keep each folder's PDFs beside its folders, with their size, content hash and revision; a listing kept before #11 has no PDFs and is listed afresh once. The one new endpoint is `files/download` on `content.dropboxapi.com`, its argument (the file's revision, `rev:…`, so the bytes are exactly the ones listed) in the `Dropbox-API-Arg` header, renewed on a 401 as every call is. A reply of another size than the listing's is refused, so a download cut short is never kept. The download is held in memory once and written to Caches (`SheetPDFs`); Dropbox's content hash names the file on the Duo but is not checked against the bytes, since the revision already pins them.

## Amendment (#12): upload, move and delete

Syncing canvases adds three endpoints to `DropboxSession`, each one request, renewed on a 401 as every call is, and losing every race to a sign-out: `files/upload` on `content.dropboxapi.com` (one file up to 150 MB, its mode `add`, `overwrite` or `update` with a revision, `mute` so the laptop isn't notified of every part), `files/move_v2` (a deleted canvas's folder into `Vellum/.deleted`, `autorename` on) and `files/delete_v2` (a generation of log parts a newer snapshot replaced). A 409 that is a conflict, or a path not found, is an answer rather than an error. An upload's `Dropbox-API-Arg` header escapes every character past ASCII as `\uXXXX`, as Dropbox requires, so a canvas named "Café" uploads. No folder is created first: an upload makes the folders on its path. No new secret: the app key reaches the app as before, and sync uses the app's one session, so signing out stops it.
