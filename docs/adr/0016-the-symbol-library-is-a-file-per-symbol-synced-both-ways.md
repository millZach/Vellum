# The symbol library is one small file per symbol, kept on the Duo and synced both ways with `Dropbox/Vellum/Symbols`

Zach decided on #41 (2026-11-06) that the symbol library lives in `Dropbox/Vellum`, is shared by every canvas, has a copy on the Duo so it works offline (ADR-0010), and that the laptop can add symbols later. A placed symbol is plain ink, so the library is the only thing about symbols that is kept, and the only thing two machines write. We considered keeping the whole library in one file, which is simplest to read but makes every save upload the whole library and turns any edit on both sides into a conflict over everything; and keeping symbols inside each canvas, which would not be one library. We chose one small file per symbol.

## The format

- **Where.** On the Duo, `Application Support/Symbols/<id>.vsym`; in Dropbox, `Vellum/Symbols/<id>.vsym`. A symbol saved on the Duo is named by a lower-case UUID. A file the laptop puts there is a symbol under whatever name it has (`Y-strainer.vsym`), and the name of the file, not the id inside it, is its id, so a file copied under a new name is a new symbol.
- **What.** JSON a person or a script can write (`SymbolFile`): `format` (1), `id`, `name`, `printedSize` in printed inches (the width it prints across), optional `tagLetters` (an instrument bubble's `FT`), and `parts`, each one of `line` (points), `circle` (x, y, r), `arc` (x, y, r, start, end in radians, y down), `text` (x, y, letter height, with `letters` and an optional `box` of its text box's width and height) or `tag` (x, y, letter height). Every coordinate is in units of the symbol's width, centred on (0, 0), y running down, so a symbol places at any size. Keys are sorted and numbers written as the shortest digits that read back exactly, so the same symbol always has the same bytes. A file Vellum can't read is skipped, never fatal: a newer `format`, a printed size of 0 or past 48" (past the long side of ARCH E1, the largest paper Vellum knows), or any coordinate, radius, angle, letter height or box size that is not finite or is past 1,000 units of the symbol's width (a drawing saved from ink is about a unit square, at most 4 units tall) is refused, so the flyout never meets a number it can't draw.
- **The six starters** (gate, ball and control valves, instrument bubble, junction box, motor) are built into the app and are not files. They don't sync: every Duo has them, and the laptop never needs to write them.

## The sync (`SymbolSync`)

- **Two ways, file by file.** One `files/list_folder` of `Vellum/Symbols` gives each file's Dropbox content hash; the Duo works out the same hash for its own files (`DropboxContentHash`), and a small ledger (`Application Support/Sync/symbols.json`) holds each file's hash when both sides last agreed. From those three (`SymbolSyncPlan`): a file only the Duo has goes up; one only Dropbox has comes down; one the same on both moves nothing; one changed on one side since they agreed goes the other way; one changed on both is kept twice, Dropbox's under its name and the Duo's as a new symbol named "… (Duo)", which goes up. A download is checked against its listed hash before it is kept. So only new or changed files move, and a sync with nothing new is the one listing.
- **Nothing is deleted by a sync.** A file one side lacks is copied from the other, so a symbol deleted on the laptop comes back from the Duo. Deleting symbols is not built; when it is, it needs its own decision.
- **When.** When the app starts, after each Save as symbol, when the app comes back to the foreground, when the connection returns, and on sign-in. All of it runs off the main thread, as does reading and writing the library's files.
- **Offline.** The listing fails and nothing moves or changes; a symbol saved offline is a file on the Duo, placed from at once, and goes up at the next sync with a connection.

This is the one place where the laptop writes and the Duo reads: ADR-0010's "the Duo is the only writer" stays true for canvases.
